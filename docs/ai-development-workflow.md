# AI エージェントを使った開発ワークフロー

このドキュメントは、個人開発で Claude Code をどのように使っているかを、トップページより一段詳しく説明するものです。
「AI に丸投げする」のではなく「AI を開発エージェントとして管理し、成果を検証してから取り入れる」進め方を、実際に行っている運用に基づいて書いています。

## 1. 使っているツール

- **Claude Code**（Anthropic の CLI エージェント）を個人プロジェクトの主なエージェントとして使っています。
- Codex CLI は別プロジェクトで併用していますが、本ポートフォリオで紹介する個人プロジェクトでは使っていません。
- Git / GitHub でバージョン管理し、変更はコミットメッセージに目的（feat / fix / docs / chore）を付けて記録しています。

## 2. 役割分担

| AI エージェントに任せている部分 | 自分が担当・判断している部分 |
|---|---|
| 技術調査、実現方法の検討、設計検討 | 何を作るか、どの機能が必要か、仕様 |
| 既存コードの解析、コード生成、複数ファイルにまたがる実装 | AI への指示（依頼文、制約、停止条件） |
| 修正、エラー原因の調査、デバッグ、リファクタリング | 生成結果の確認、問題の原因の切り分け、修正方針の決定 |
| テストコードの作成、ドキュメント整備 | 実環境での動作確認、最終的な取捨選択の判断、継続改善 |

AI が出した計画や修正案は、そのまま受け入れず内容を読み、必要なら方針を変えて指示し直します。
逆に、実装の細部（ファイル横断の変更、ライブラリの使い方、テストの書き方）は AI に委ね、自分は結果を検証する側に回ります。

## 3. ルールを積み上げる仕組み

毎回ゼロから指示するのではなく、次の 2 層のルールファイルをエージェントに読み込ませています。

### 3.1 全プロジェクト共通のルール

すべてのプロジェクトに共通する安全ルールと進め方を 1 つのファイルにまとめ、各プロジェクトから参照しています。主な内容は次のとおりです。

- 破壊的なコマンド（ファイルの一括削除、履歴の強制書き換えなど）は実行前に必ず確認を取る
- 秘密情報（API キー、認証情報）は `.env` などから読み、プロンプト・コード・出力に直接書かない
- `git add` は対象ファイルを明示し、コミット前にステージ内容を確認する
- push の前には、個人情報・機密・大容量ファイル・コミット粒度・非可逆操作の 5 点を確認する
- 「調査だけ」「レビューだけ」の依頼ではコードや設定を変更しない
- 計画 → 実装 → 検証の順で進め、動作確認なしに完了扱いにしない

### 3.2 プロジェクト固有の CLAUDE.md

各プロジェクトのルート直下に CLAUDE.md を置き、そのプロジェクトの前提をまとめています。例えば次のような内容です（本体は非公開）。

- アーキテクチャ図と主要ディレクトリの役割
- セットアップ・実行・テストのコマンド
- 設計判断とその理由（データのスキーマ、ローテーションの方式、音声ミックスの順序など）
- 開発時の注意点（ライブラリの落とし穴、クラッシュしやすい条件）
- 定時実行やデプロイに関する運用ルール（本番稼働中に触ってはいけない設定など）
- エージェントに許可する操作の範囲（最小権限の設定）

## 4. 進め方

### 4.1 依頼文をファイルで渡す

まとまった作業は、チャットに直接打ち込むのではなく、依頼文を Markdown ファイルに書いてから渡しています。
依頼文には次を含めます。

- 目的と背景
- 対象ファイル・対象範囲と、触ってはいけない範囲
- 制約（既存の挙動を変えない、依存関係を増やさない、など）
- 停止条件（ここまで進んだら止まって確認を待つ）
- 完了の定義（どのテストが通れば完了か、何を報告するか）

過去の依頼文はプロジェクト内に保存しており、後から「なぜこの変更をしたか」を辿れるようにしています。

### 4.2 フェーズ分割と承認

大きな作業は「調査 → 計画提示 → 承認 → 実装 → 検証 → 報告」のフェーズに分け、フェーズの区切りでエージェントを止めて内容を確認します。
計画の段階で「対象ファイル・変更内容・影響範囲」を出させ、納得できない場合は実装に進ませません。

### 4.3 作業記録と教訓

各プロジェクトに次の 2 つの記録ファイルを置いています。

- **計画・チェックリスト**: 実装前に計画を書き、各ステップの完了を更新する
- **教訓の記録**: 障害やミスが起きたら「何が起きたか」「根本原因」「再発防止のルール」を残す

教訓は「〜の場合は〜する」の形まで落とし込み、次回以降の依頼文や CLAUDE.md に反映します。
自分で気づいたミスだけでなく、エージェントの誤りも同じ形式で記録します。

### 4.4 検証してから取り入れる

エージェントの変更は、次のような方法で確認してから取り入れます。

- 単体テストの実行（Python の unittest など）や型チェック
- `grep` による全数確認（修正漏れがないか、同じパターンが他に残っていないか）
- 実環境での動作確認（定時実行を実際に走らせる、通知が届くか確かめる、実機のブラウザで操作する）
- 変更差分の確認と、仕様との整合の確認

「テストが通った」だけでは完了にせず、実環境で動いたことを確認してからコミットしています。

### 4.5 読み取り専用の調査を分離する

コードベースの調査やログの集計は、書き込み権限を持たない調査用のサブエージェントに任せ、結果だけを受け取ることがあります。
調査と変更を分けることで、調査のつもりが変更になってしまう事故を防ぎ、複数の観点から並列に監査することもできます。

## 5. 依頼文の例（匿名化・簡略化）

実際の依頼文を、内容を一般化して 2 件示します。

### 例 1: 品質ゲートの強化

```text
目的:
  生成した動画の長さが上限を超えた場合、現在は警告を出して続行している。
  公開後に取り消せないため、上限超過を「失敗」として扱い、再生成に回したい。

対象:
  pipeline/ 配下の尺検査と再生成の処理。Remotion 側のコンポーネントは触らない。

制約:
  - 既存のテストを壊さない。新しい挙動にはテストを追加する。
  - 再生成の上限回数は既存の設定値を使う。
  - 実験期間中のため、仕様変更はログファイルに追記する。

進め方:
  1. 現状の処理と影響範囲を調査し、変更計画を提示して止まる。
  2. 承認後に実装し、テストを実行して結果を報告する。
```

### 例 2: 本番障害の原因調査（変更禁止）

```text
目的:
  昨日の定時実行が失敗した。原因を調べてほしい。

条件:
  - 調査のみ。コード・設定・記録ファイルは変更しない。
  - ログと直近のコミット差分から、失敗した段階と原因の候補を挙げる。
  - 確定した原因と推測を分けて報告する。
  - 修正案は提示だけにとどめ、実装は次の依頼で判断する。
```

## 6. うまくいっている点と気をつけている点

- 依頼文に「触らない範囲」と「停止条件」を書くと、想定外の変更が大きく減りました。
- エージェントの報告は事実と推測を分けさせ、「動くはず」ではなく「動いた」ことを根拠付きで報告させています。
- 教訓を CLAUDE.md や共通ルールに戻すことで、同じミスの再発が減りました。
- 一方で、ルールを増やしすぎると読み込みが重くなるため、共通ルールとプロジェクト固有ルールの二層に分け、重複を避けています。
